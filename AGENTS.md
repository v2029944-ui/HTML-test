# Инструкции ИИ-агентам — HTML-test

Основная платформа — Windows **Tauri 2 / Rust / SQLite** в `tauri/`. Корневой `index.html` служит исходником интерфейса Tauri и сохраняет самостоятельный запуск в браузере. При доработках сохраняйте эту самостоятельность, защищайте данные от случайной потери, сохраняйте резервное копирование, работу с Excel и проверки целостности данных. Не сливайте незаконченные Draft PR и не включайте функциональность в рабочий интерфейс, пока не прошли соответствующие проверки.

## Текущая архитектура интерфейса

- [tauri/prepare.cjs](tauri/prepare.cjs) через [tauri/unified-build.cjs](tauri/unified-build.cjs) создаёт `tauri/web/index.html` и ресурсы из корневого HTML и модулей Tauri. Редактируйте исходники, а не генерируемый `tauri/web/`; проверяйте результат подготовки интерфейса.
- Рабочий интерфейс использует `unified-*`, `reference-*` и вспомогательные native-модули, перечисленные в сборке. Старые `startup.html`, `native-workspace.html` и часть `native-*.js` не входят в установленное приложение. Перед изменением определяйте фактическую точку входа и потребителей модуля; одно наличие файла или теста не подтверждает его использование в приложении.
- SQLite — основной источник данных Tauri. [unified-base.js](tauri/unified-base.js) подготавливает индексы порциями и раздаёт ревизию экранам; аналитика читает ограниченные SQL-результаты. Не возвращайте старую полную загрузку истории через `load_data` / `desktopAPI.load()`.

## Совместимость версий во время разработки

**Программа ещё находится в стадии разработки. Обратная совместимость между версиями не требуется и не является условием слияния PR или выпуска новой версии.** Разрешено менять структуру SQLite, форматы внутренних данных, интерфейс и API без поддержки прежних экспериментальных выпусков (включая обновление с 0.1.3). Не тратьте время на обязательные миграции, поддержку старых установщиков и тесты обновления между версиями, если владелец отдельно этого не запросил.

Это **не отменяет** обязательных проверок работы текущей версии, целостности данных, транзакционности импорта, резервного копирования и отказа от случайного удаления/перезаписи файлов. Если изменение несовместимо с ранее созданными данными, ясно укажите это в release notes; не обещайте автоматический перенос. Никогда не удаляйте реальные пользовательские данные без отдельного разрешения.

## Обязательное правило выпуска новой версии

**При выпуске каждой новой версии необходимо создать отдельный GitHub Release с Windows-установщиком и указать, что конкретно изменилось в версии.** Одного EXE в Actions, изменения номера в коде или PR недостаточно. Проверьте, что Release и артефакты доступны, обновите ссылки в README. Нельзя утверждать, что выпуск состоялся, если релиз не опубликован.

Соблюдайте **[полный порядок выпуска](docs/RELEASE_POLICY.md)**: новый уникальный номер, реальные release notes, успешные CI/GUI/данные-проверки, согласие владельца перед публикацией, подписание перед переводом канала онлайн-обновлений. При невозможности завершить выпуск явно указывайте блокирующие причины и не переключайте `tauri-updates`.

Не добавляйте секреты, реальные пользовательские файлы Excel/SQLite или тестовую сборку с WebView2 CDP в Releases.

## Дополнительные ограничения Codex

Перед работой читать [docs/CODEX_SAFETY_RULES.md](docs/CODEX_SAFETY_RULES.md). Эти правила применяются и к задачам из [issue #79](https://github.com/v2029944-ui/HTML-test/issues/79).

- Все изменения — в отдельной ветке через PR. **Не изменять напрямую `main`, не выполнять force-push, слияние или закрытие чужих задач без подтверждения владельца.**
- Нельзя самостоятельно публиковать Release, запускать подписанный `publish`, переиспользовать тег, переключать `tauri-updates`, изменять секреты и правила защиты GitHub.
- Для SQLite, импорта Excel, удаления отчётов, бэкапов, восстановления и updater — отдельный PR с оценкой рисков, тестами отказов и сохранности данных.
- Сохранять автономный `index.html`, корректность `null` и ограниченные SQL-запросы. Нельзя заменять отсутствие данных нулём, ослаблять тесты или скрывать известные ошибки.
- Не коммитить реальные пользовательские Excel/SQLite/JSON, секреты, подписанные установщики и диагностические сборки.
- **Не добавлять «Историю импортов» и «Сохранённые наборы фильтров» без нового задания:** эти возможности ранее исключены.

При архитектурном ревью Rust используйте [deslop-please](README.md#разработка-и-проверки) для анализа зависимостей. Сопоставляйте предупреждения с реальными вызовами и проверяйте поведение штатными тестами.

Наличие AGENTS.md само по себе не заменяет GitHub Rulesets: владельцу следует дополнительно защитить ветку `main`.

## SQL-скиллы Codex

Используйте проектные скиллы из `.agents/skills/` по задаче, не загружайте все подряд:
- `$sql-optimization` — медленные запросы, индексы и замеры.
- `$sql-code-review` — ревью SQL и анализ зависимостей перед изменением схемы.
- `$sqlite-tauri-expert` — изменения хранения, импорта, агрегатов, бэкапов и SMB.

При пересечении задач подключайте дополнительный скилл только для соответствующего этапа; при обычных изменениях UI без SQL они не нужны. Правила безопасности выше имеют приоритет. Скиллы не разрешают доступ к рабочей базе или внешние установки.

## UI-скиллы Codex

- `$frontend-design` — компоновка, темы, типографика и компоненты.
- `$ui-ux-review` — визуальная проверка, доступность и регрессии.
- `$tauri-dashboard-expert` — таблицы, графики, фильтры и взаимодействие Tauri/IPC.

Выбирайте один основной скилл по задаче; подключайте другие только при необходимости. Для чисто SQL-задач UI-скиллы не нужны. Используйте существующие тесты; не устанавливайте Playwright/Figma или новые зависимости автоматически.

## Учёт выполнения задач

Единственный актуальный план — [issue #79](https://github.com/v2029944-ui/HTML-test/issues/79). После фактического выполнения задачи и прохождения обязательных проверок отметьте её `- [x]` вместо `- [ ]`, перенесите в раздел «Выполненные задачи» в конце плана, сохраните ID и укажите PR/коммит, результаты проверок и оставшиеся ограничения. Не отмечайте частично выполненные задачи, задачи с непрошедшими обязательными проверками или без подтверждённого слияния, если оно требуется для приёмки. Архивы #185, #193 и #199 не обновляйте. Если редактирование #79 недоступно, сообщите об этом и укажите ID для обновления. Перед записью перечитайте актуальный план, чтобы не затереть параллельные изменения. Это правило не разрешает слияние PR или выпуск без согласия владельца.

Различайте наличие реализации, проверки на конкретном SHA, слияние в `main` и публикацию выпуска. Исследование, подготовленный план, наличие теста или старый успешный CI сами по себе не подтверждают завершение задачи.
