# Расширяемые виды отчётов Tauri (экспериментальный SQL-режим)

## Назначение

**Вид отчёта** (например, трудозатраты или план/факт) теперь отделён от **периодичности** (день, неделя, месяц). У каждого вида собственные имена, единицы измерения, входные показатели и вычисляемые отношения. Важно: существующая классическая аналитика `count/amount` пока **не переведена** на новый движок. Система видов работает параллельно в отдельном SQL-интерфейсе.

Для **добавления нового вида без изменения Rust и HTML**:

1. Добавить объект в `tauri/src-tauri/src/metric-kinds.json`, указав `id`, `name`, `dimensionLabel` и `metrics`.
2. Указать для исходных показателей `operation: "sum"`; для производных — `operation: "ratio"`, `numerator`, `denominator` и необязательный `factor` (например, 100 для процентов).
3. Для построчной Excel-таблицы добавить **профиль столбцов** в `tauri/src-tauri/src/metric-xlsx-profiles.json` (подробности ниже). Для другого формата данных остаётся нормализованный JSON.
4. Открыть SQL-режим Tauri → «Дополнительные виды отчётов» → выбрать профиль XLSX, указать даты, выбрать файл → проверить показатели → подтвердить сохранение. Аналитика затем рассчитывается по выбранному виду без нового SQL-кода.

Пример нового описания (показатели можно называть по-русски; технические ID — латиницей):

```json
{
  "id": "fuel",
  "name": "Расход топлива",
  "dimensionLabel": "Техника",
  "metrics": [
    {"id":"liters","name":"Топливо","unit":"л","operation":"sum"},
    {"id":"kilometers","name":"Пробег","unit":"км","operation":"sum"},
    {"id":"liters_per_100km","name":"На 100 км","unit":"л/100 км",
     "operation":"ratio","numerator":"liters","denominator":"kilometers","factor":100}
  ]
}
```

## Шаблоны Excel — без нового импортёра

Новый файл `tauri/src-tauri/src/metric-xlsx-profiles.json` хранит определения построчных Excel-таблиц. Для **нового расположения столбцов** достаточно добавить ещё один объект в массив. Профили встроены в сборку Tauri, подгружаются в интерфейс автоматически и проверяются Rust до чтения данных.

Пример для нового вида **«Расход топлива»** из примера выше:

```json
{
  "id": "fuel_table",
  "kind": "fuel",
  "name": "Расход топлива — основной лист",
  "sheet": "Data",
  "headerRow": 1,
  "firstDataRow": 2,
  "organizationColumn": "A",
  "dimensionColumn": "B",
  "values": { "liters": "C", "kilometers": "D" },
  "headers": {
    "A": "Подразделение",
    "B": "Техника",
    "C": "Литры",
    "D": "Пробег"
  }
}
```

При таком профиле Excel должен выглядеть следующим образом:

| A — Подразделение | B — Техника | C — Литры | D — Пробег |
|---|---|---:|---:|
| СМУ16 | Экскаватор | 120 | 300 |
| АВТО | Грузовик | 80 | 450 |

Наименования листа и заголовков проверяются перед импортом, чтобы не перепутать значения. Все поля из `values` должны совпадать с исходными (`sum`) показателями выбранного вида. `ratio`-показатели **не** читаются из Excel — они рассчитываются из сумм исходных значений. Каждому показателю — отдельный столбец (A, B, C и т. д.). Поле `organizationColumn` необязательно; `dimensionColumn` обязательно. Если таблица содержит строку «Итого», можно задать `lastDataRow`, чтобы ограничить чтение конкретными строками.

**Как использовать:** заполнить даты начала и конца периода в разделе дополнительных отчётов → выбрать шаблон → «Выбрать XLSX по шаблону» → проверить сводку → «Подтвердить импорт». Даты задаются пользователем, а не извлекаются по догадке из названия файла. Для второго отчёта с другим видом/столбцами добавляется ещё один профиль; изменения парсера или интерфейса не нужны.

Под капотом Excel обрабатывается тем же **ограниченным дисковым XLSX-парсером**, что и нативный импорт: не загружается весь лист в WebView, хранится только одна строка при преобразовании, ограничен объём архива, распакованных данных и количество сохранённых строк. Отчёт сохраняется в SQLite атомарно **только после предпросмотра и повторной проверки источника**. Формулы в назначенных ячейках, несовпадающие заголовки, отсутствующие числовые значения и некорректные числа отклоняются с указанием строки или ячейки.

**Граница конфигурации:** поддерживаются простые таблицы «одна строка = объект с показателями». Многорядные заголовки, горизонтальные даты, иерархические блоки и сложные вычисления требуют отдельного преобразователя — шаблона столбцов для этого недостаточно. Новый профиль требует пересборки программы; пользовательский редактор профилей пока не реализован.

## Универсальный формат данных для адаптеров

Файл в UTF-8, не более 8 МиБ и 10 000 строк на один импорт. Образец: `tauri/examples/labor-report.json`.

```json
{
  "kind": "labor",
  "id": "labor-2026-11-18",
  "start": "2026-11-18",
  "end": "2026-11-18",
  "sourceName": "Трудозатраты.xlsx",
  "rows": [
    {"organization":"СМУ16","dimension":"Монтаж","values":{"hours":8,"units":16}},
    {"organization":"АВТО","dimension":"Ремонт","values":{"hours":4,"units":3}}
  ]
}
```

В каждой строке обязательны **ровно все исходные** (`sum`) показатели из каталога, без производных. `organization` может быть `null`. Производные показатели вычисляются **после суммирования** исходных значений; проценты и средние не складываются. При нулевом знаменателе отображается отсутствие значения, а не выдуманный ноль.

SQLite создаёт отдельные `metric_report_docs` / `metric_report_values` и revision. Данные не смешиваются с `reports` / `report_rows`, и поэтому не меняют текущие отчёты, графики или импорт Excel. Импорт требует предварительный просмотр и подтверждение. Перед записью Rust повторно читает источник и проверяет SHA исходника, описание вида и ревизию SQLite; отчёт с уже существующим ID не заменяется; повторные или перекрывающиеся периоды от того же источника отклоняются, чтобы избежать двойного счёта. Разные источники за один период допустимы. Запись транзакционная.

## Текущие ограничения

- Встроен **каталог определений** в составе приложения; это не запуск недоверенных внешних плагинов и не пользовательский редактор формул.
- Поддерживаются только аддитивные числа и отношения двух их сумм. Другие формулы (медиана, уникальные пользователи, взвешенная средняя с условиями), временные ряды и полнота периодов требуют новых правил. Простые индивидуальные Excel-колонки уже задаются профилем.
- Нормализованный JSON ограничен 8 МиБ. XLSX обрабатывается дисковым парсером с лимитом архива 30 МиБ, не более 10 000 нормализованных строк на один импорт и дополнительными лимитами обработки ZIP/XML. Неизвестные форматы Excel не поддерживаются автоматически.
- Исторические версии программы не поддерживаются как обязательная совместимость, но сохранность данных текущей версии и тесты резервного копирования обязательны.
- Изменение/удаление ID показателей или вида в каталоге делает ранее импортированные значения недоступными для корректного расчёта: менять их следует осознанно. Отдельный механизм версионирования определений — будущая задача.
- В SQL-режиме пока только общий итог по выбранному виду и диапазону, не детальная расшифровка по каждому подразделению. Нулевое количество отчётов даёт прочерк, **не** нулевой итог.

Проверка: `cargo test --manifest-path tauri/src-tauri/Cargo.toml metric_` и `node --test tauri/tests/native-metric-kinds.test.cjs`, затем Windows Actions с установленным WebView2. Это Draft-механизм, без изменений в `main` или релизах.
