# Release policy — «Анализ работ»

Правила обязательны для всех ИИ-агентов и разработчиков, выпускающих Windows-версию Tauri. Применяйте их независимо от инструмента сборки или доступности GitHub Actions.

## Обязательное условие каждого нового выпуска

**Нельзя объявлять новую версию опубликованной, если для неё не создан отдельный GitHub Release в `v2029944-ui/HTML-test`, не приложен доступный для скачивания Windows-установщик и не опубликовано описание фактических изменений.** GitHub Actions artifact, коммит, PR, каталог `downloads/` или только изменение версии не заменяют GitHub Release.

1. Согласуйте новый номер в `tauri/package.json`, `tauri/src-tauri/Cargo.toml` и `tauri/src-tauri/tauri.conf.json`. Не переиспользуйте номер или тег для изменённого установщика.
2. Подготовьте **заметки к именно этой версии**: что добавлено, что исправлено, что изменилось в интерфейсе, хранении/импорте/экспорте, какие ограничения и известные ошибки остаются, что пользователю делать при обновлении. Не используйте универсальный текст «экспериментальная версия» без списка изменений. Укажите совместимость с предыдущей версией и необходимость резервной копии, если затрагиваются данные.
3. Запустите Node.js и Rust-тесты, Windows NSIS-сборку и GUI smoke в WebView2 **на точном коммите выпуска**. Проверьте результаты, а не только факт запуска Actions. Для операций с данными требуются проверка миграции и восстановления на копиях тестовой/старой SQLite, контроль больших Excel, предотвращение потери данных. Не выдавайте непроверенные сценарии за пройденные.
4. После явного разрешения владельца опубликуйте **отдельный версионированный GitHub Release**, например `tauri-v0.1.4`, и приложите установщик (и файл `.sig`, если сборка подписана). Текст релиза должен содержать реальные изменения; отметьте тестовый релиз как prerelease, если он не готов к рабочему использованию.
5. Проверьте через GitHub API или UI, что релиз существует, файлы доступны, имена и номер версии совпадают, и описание содержит список изменений. Скопируйте ссылку в `README.md` и `tauri/README.md` только после подтверждения публикации. Сообщите пользователю ссылку, версию и краткое содержание изменений.
6. **Онлайн-обновление включайте только после публикации и проверки подписанного релиза**, совпадения подписи/версии и наличия всех артефактов. `tauri-updates` — канал обновления, не замена версии в Releases. Нельзя направлять его на неподписанный установщик или тестовую сборку с включённой диагностикой WebView2.
7. Если проверки/подпись/разрешение недоступны, оставьте выпуск в статусе **не опубликован**, сообщите причину и не меняйте канал обновления. Не утверждайте, что версия выпущена, пока фактическая публикация не подтверждена.

## Технические ограничения

- Сохраняйте `index.html` как самостоятельную HTML-версию и исходные пользовательские данные; не включайте настоящие базы и Excel в релиз.
- Для Windows x64 используйте обычную сборку NSIS. Диагностический WebView2/CDP bundle предназначен **только для CI** и никогда не размещается в Releases.
- `tauri/release.cjs` подготавливает подписанный артефакт, а `tauri/publish.cjs` размещает файлы в GitHub и после этого обновляет канал. Тестовый неподписанный установщик можно выпускать как **отдельный prerelease для ручной установки**, без изменения `tauri-updates`, при соблюдении пунктов выше.
- Никогда не публикуйте токены и закрытые ключи. При подозрении на сбой публикации проверяйте существующий релиз, а не перезаписывайте файл под прежним номером.
