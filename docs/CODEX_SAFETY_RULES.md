# Ограничения Codex и защита HTML-test

Обязательные инструкции для ИИ-агентов. Главная платформа — Windows **Tauri 2 / Rust / SQLite**, автономный `index.html` остаётся самостоятельным. Этот документ дополняет [AGENTS.md](../AGENTS.md) и [RELEASE_POLICY.md](RELEASE_POLICY.md).

## 1. Разрешено без отдельного согласия

Изучать репозиторий, создавать **рабочие ветки и Draft PR**, исправлять код в рамках одной задачи, писать тесты, запускать проверки, обновлять документацию и комментировать прогресс. Не заменять работу коллег и не переписывать чужие коммиты. Для задач из [#79](https://github.com/v2029944-ui/HTML-test/issues/79) проверять фактический `main`, открытые PR и CI, прежде чем дублировать уже внесённое.

## 2. Запрещено без явного разрешения владельца

- Прямой push в `main`, force-push, переписывание истории, удаление чужих веток, обход CI/branch protection.
- **Слияние любого PR**, в том числе не-Draft; закрытие или удаление задач с работой другого участника. Draft нельзя сливать.
- Создание/изменение релизов и тегов, публикация EXE, запуск `operation=publish`, переключение `tauri-updates`, изменение signing keys, секретов или прав GitHub.
- Удаление, перезапись или массовое изменение настоящих пользовательских Excel, SQLite, резервных копий и настроек источников. Никаких экспериментов на рабочей базе — только на изолированных тестовых копиях.
- Удаление автономного `index.html` или ослабление подтверждений импорта, резервирования, безопасного восстановления и регрессионных тестов ради упрощения интерфейса.
- Коммит реальных пользовательских файлов, приватных журналов, ключей, токенов, EXE и тестовых WebView2/CDP-сборок.
- Расширение объёма задачи без решения владельца; в частности, **«История импортов» и «Сохранённые наборы фильтров» не входят в текущий план**.

## 3. Изменения высокого риска — отдельный PR

| Область | Необходимые проверки |
| --- | --- |
| SQLite, Rust, схема и агрегаты | Транзакции, `null` ≠ 0, WAL, восстановление на копии, стабильность итогов, ошибки |
| Excel, правила папки, импорт и удаление | Отмена, дубли, неоднозначные даты, превышение лимитов, повторная загрузка, повреждённые файлы |
| Резервные копии и восстановление | Проверка целостности, защитная копия, недостаток места, отказ записи, безопасный откат |
| Updater, подписание, `.github/workflows/`, `tauri/release.cjs`, `tauri/publish.cjs` | Только отдельное разрешение на выпуск, уникальный номер, точный SHA CI, подписанный EXE и SIG |
| Tauri UI, SQL-графики и `index.html` | Node/WebView2 регрессии, масштаб/фокус/CSV, сохранение самостоятельной браузерной версии |

**Совместимость с каждым прежним экспериментальным выпуском не обязательна**, согласно AGENTS.md. Но несовместимость должна быть обозначена в release notes, а реальные пользовательские данные нельзя удалять или переписывать без разрешения.

## 4. Инварианты данных и поведения

- Пропуск отчёта, ошибочный отчёт, замечание импорта и подтверждённый ноль — **разные состояния**. Не изображать неизвестное значение как `0`.
- Недельные/месячные итоги не распределять автоматически по дням.
- Не угадывать единицы измерения, валюту, даты или структуру Excel; не объединять одноимённые или похожие работы без проверки и согласования.
- Сохранять атомарность импорта, проверку выбранного файла и защиту от повторной записи по старому подтверждению.
- Для большой истории — ограниченные SQL-запросы и страницы; не загружать все `reports.json`/всю SQLite-историю в JS.
- Не ослаблять ограничения размера, тесты защиты или правила публикации ради зелёного CI.

## 5. Порядок работы Codex

1. Одна задача → одна логичная ветка/PR. Сначала воспроизведение ошибки, затем минимальные изменения и тест.
2. Точно указать затронутые файлы, изменение поведения и возможное воздействие на данные.
3. Выполнить проверки **по риску**: docs-only — ссылки/структура; JS/UI — Node + frontend и при необходимости установленный WebView2; SQLite/импорт — Rust/Node, ошибки/отмена, Windows CI; релиз — весь порядок [RELEASE_POLICY.md](RELEASE_POLICY.md).
4. **Тесты должны относиться к последнему SHA.** `cancelled`, старый `success` или один прошедший frontend-этап не дают оснований объявить весь PR проверенным.
5. В PR заполнить чек-лист: SHA, проверено/не проверено, границы изменений, тесты, известные риски. При незавершённой функциональности или неполной приёмке оставить Draft.
6. После review владелец отдельно решает, что сливать; затем отдельно разрешает выпуск с точным номером версии.

## 6. Техническая защита GitHub, включаемая владельцем

В `Settings → Rules → Rulesets` создайте правило для ветки **`main`**: Require pull request, Block force pushes, Block deletions. Рекомендуется Require status checks (`check-sensitive-files`, после включения workflow `PR safety`), при наличии review-процесса — Require conversation resolution.

**Важно:** текущий Windows workflow запускается на pull_request только при изменениях `tauri/**`, `index.html`, `tests/**` и собственного YAML. Его нельзя делать универсально обязательным для docs-only PR без изменения триггеров: проверка иначе зависнет в Pending. Но для Tauri-кода полный Windows `verify-and-build` обязателен по процессу перед merge.

Если репозиторием управляет один человек, **не задавайте обязательное независимое одобрение** без второго reviewer: автор не сможет одобрить собственный PR. Для команды можно включить минимум 1 approval и dismiss stale approvals. Не выдавать агентам обход ограничений.

Новый `PR safety` — только быстрая защита от случайных коммитов баз, ключей, Excel и установщиков; **она не заменяет code review и тесты приложения**. Правила ветки через интеграцию могут быть недоступны: нельзя утверждать, что они включены, не проверив настройки.

## 7. Выпуск

Новый уникальный номер и release notes, полный CI **на точном коммите `main`**, отдельное разрешение владельца на публикацию, подпись EXE и проверка SIG, GitHub Release с реальными изменениями, проверка канала обновлений. **Не перезаписывать 1.8.0 и не публиковать диагностический GUI-бандл.**
