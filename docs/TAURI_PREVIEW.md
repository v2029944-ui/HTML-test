## Интерфейс

Нативные `select` сохраняют идентификаторы, опции, обработчики `change`, клавиатурный ввод и доступность. Их поля и списки множественного выбора используют общие цвета, границы, высоты, скругления, стрелки и состояния выбора. В WebView2/Chromium с поддержкой `appearance: base-select` браузер также оформляет раскрытые опции общими переменными темы. В старых движках работает нативный fallback: системное окно списка может отличаться в деталях оформления. Никакая библиотека селектов не добавлена.

## Обновления

Используется существующий Tauri Updater, тот же URL канала и существующий открытый ключ проверки. После загрузки данных проверка запускается автоматически, но скачивание и установка — только после подтверждения. В HTML-браузерной версии Tauri-уведомлений нет.

Уведомление содержит «Что нового», «Позже» и «Обновить». Описание из манифеста выводится обычным текстом, без исполнения HTML. Если описания нет, это явно указано. «Позже» сохраняет номер версии в отдельном локальном предпочтении `work-reports-update-deferred-v1`; следующая версия уведомит снова. Индикатор в «Управлении» остаётся видимым, а ручная проверка вновь показывает уведомление. Недоступность предпочтений не блокирует приложение и не создаёт ложного сообщения об успешном сохранении отсрочки.

Причина блокировки, прогресс загрузки и ошибки установки, включая отказ проверки подписи, отображаются также в уведомлении на главной «Аналитике», а не только в скрытых «Настройках».

Во время чтения/ручной проверки Excel и незавершённых записей данных установка запрещена. Tauri bridge считает незавершённые записи SQLite и правил и чтения Excel; счётчики освобождаются также при ошибке. На время подтверждения и установки новая запись/импорт запрещены; занятость повторно проверяется после ответа на подтверждение. При ошибке подписи/сети интерфейс разблокируется. Проверку подписи выполняет Tauri Updater; отключения проверки нет.

Схема SQLite, финансовые расчёты, правила разбора Excel, данные и формат резервных копий не менялись.

## Проверки

Локально:

```
node --test tauri/tests/*.test.cjs tests/*.cjs
PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -v
```

Для актуальной структуры репозитория приведена команда без удалённых Electron-тестов. Исторический запуск Windows CI выполнялся на прежнем составе файлов; результаты проверки остаются историческими и не являются проверкой обновлённого PR. Rust/Windows проверяются существующим Tauri workflow в выделенной тестовой ветке. Его подписанная сборка вызывает `build:signed:windows`, но **не вызывает `publish.cjs`**. Ключи не включаются в исходники или артефакты.

`tauri/tests/windows_smoke.py` запускается только в изолированном Windows CI: устанавливает EXE в временную папку, запускает настоящий WebView2, подключает Playwright через локальный отладочный порт, импортирует синтетический годовой XLSX, проверяет SQLite, клавиатуру списков, високосный февраль и повторный запуск. При непустой базе проверка останавливается без замены данных. Отладочный порт включается **только в отдельной непубликуемой GUI-сборке** через `tauri/tests/ci-webview2.json` и `additionalBrowserArgs` WebView2. На Windows CI с WebView2 156 переменная окружения для повышенного процесса не сработала; основной подписанный preview создаётся до этого шага и не содержит отладочного порта. GUI-прогон проверяет установленную отдельно собранную Tauri-версию с тем же интерфейсом и SQLite, но не доказывает запуск именно подписанного preview в режиме DevTools.

Артефакт `Tauri-Windows-preview` содержит `setup.exe`, `setup.exe.sig`, `build-info.json` и, при успешном запуске WebView2, снимок окна. `build-info.json` фиксирует размер, SHA256, движок и реально пройденные проверки. Наличие установщика само по себе не подтверждает успешный Windows-запуск: нужно проверить результат шага smoke и содержимое отчёта. Тестовый EXE с открытым DevTools не загружается в артефакты и не публикуется. Обычный артефакт `Tauri-Windows-experimental` создаётся только вне этой тестовой ветки.

Сборка требует Node/Rust только от CI. Пользователь скачивает готовый EXE; средства разработки ему не нужны. Физический Windows 10/11, личные Excel и установка подписанного онлайн-обновления на пользовательском компьютере требуют отдельной проверки. CI не публикует этот тестовый установщик в рабочий канал.

## Ожидания состояния при строгой CSP

В Windows smoke все ожидания состояния приложения используют ограниченный по времени опрос через CDP `page.evaluate`. `page.wait_for_function` не используется: его вычисление строки внутри страницы блокировалось действующей CSP WebView2. Опрос сохраняет обработку навигации, сообщает название операции при тайм-ауте и не скрывает прочие ошибки приложения. Готовность проверяется при начальном запуске, загрузке Excel, построении предпросмотра, сохранении и после повторного запуска.

Регрессия `tests/test_windows_waits.py` проверяет ожидание асинхронного состояния в странице со строгой CSP, тайм-аут и передачу настоящих ошибок JavaScript. CSP и настройки пользовательской сборки не ослабляются.
